## 四、统一门禁判定表

审计模式默认只读，只能输出证据、发现和修复计划；审计结果涉及修改全局规则、静态记忆、模块职责、Git 设置或外部系统时，仍按本表执行确认，不得以审计名义绕过门禁。

触发后按本表判定任务门禁档位。三档互斥，自上而下先匹配"必须确认"，再匹配"问一个问题"，都不命中即为"直接执行"。

### 1. 必须确认（档三）

命中任意一条时，列出变更点并等待用户明确同意：

1. 覆盖核心业务记忆。
2. 修改静态底层记忆。
3. 改变模块职责边界。
4. 删除、合并或批量整理大量历史记忆。
5. 将项目记忆纳入 git 或修改 `.gitignore`。
6. 公共模块能力变更。

### 2. 问一个问题（档二）

命中任意一条硬停条件时，只问一个最影响实现结果的问题，得到回答后重新按本表判定：

1. 关键业务规则缺失，且无法从记忆或已有同类实现中推断。
2. 多个合理方案会导致业务结果实质不同，且无法从记忆或代码中推断取舍依据。
3. 模块归属不明，且不同归属会影响公共能力边界。

### 3. 直接执行（档一）

未命中档三、档二时，先简短说明理解、模块落点和执行路径，然后直接推进，不等待确认。典型场景：低风险微调且上下文明确；信息足够、落点明确、风险可控的研发任务；用户已确认过方案或说过"按这个做""可以，开始改"。

### 4. 全局约束

1. 同一任务内已确认事项不得重复追问或重复要求确认。
2. 用户明确说"先给方案""待我确认""不要改代码"时，只能分析、追问、输出方案，不得修改代码；该显式指令优先于本表档位判定。
3. 其他章节涉及追问或确认时均引用本章判定表，不另行定义确认条件。
