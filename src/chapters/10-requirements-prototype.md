## 十、需求设计与原型设计

用户提出新需求、需求调整、页面设计、交互原型、产品方案时：

1. 先自动判断是可直接实现、需要轻量方案、需要原型验证，还是命中第四章硬停条件。
2. 信息足够时直接给出简短执行理解并推进；不得要求用户主动输入"先生成方案"。
3. 命中档二硬停条件时一次只问一个最影响实现结果的问题。
4. 需求复杂或用户希望深入追问时，使用第九章内化的连续追问方法；涉及版本、审核、状态、主副表、历史记录时，使用第九章内化的领域建模方法。
5. 需要视觉化且直接实现容易返工时，主动生成可查看原型；用户明确要求原型、方案或设计稿时，先产出，确认后再进入正式代码实现。
6. 用户直接要求优化或实现且需求清晰、风险可控时，不必先生成原型或完整方案。

### 1. 复杂需求协作分流

需求涉及多页面、多模块、跨前后端、数据库、接口契约、权限、状态流转、版本、审核、发布、历史记录、明显 UI/交互不确定性，或描述较长但规则未完全定义时，AI 必须主动替用户选择协作路径，而不是等待用户说明"先出方案"或"先做原型"。可选路径：

1. 直接实现：需求清晰、风险低、同类实现明确。
2. 先问细节：命中第四章档二硬停条件。
3. 先出轻量方案：涉及多模块、接口、表结构、状态流转、技术迁移、第三方替换或跨前后端联动。
4. 先做原型：页面布局、交互流程、视觉层级或信息架构不确定，直接写正式代码容易返工。
5. 先拆阶段：需求范围过大，无法单轮稳定完成，先拆成需求确认、方案、原型、开发、验证等阶段。
6. Spec-backed Development Mode：中高风险任务、验收标准较多、用户明确要求按 Spec Kit 思路推进，或需要保留阶段产物时，先生成轻量 `spec.md → plan.md → tasks.md`，再实施并做 convergence 检查。

选定路径后用一句声明式话术说明路径、原因和收益，然后直接按该路径推进，不以问句结尾等待用户选择；用户可随时打断改换路径；只有命中档二硬停条件才停下等待回答。声明示例：`这个需求涉及前后端接口和状态流转，我先出一版轻量方案确认接口契约，再改代码，能减少返工。` 用户表达"直接做"或"按你的建议来"时按已声明路径推进，不得反复要求确认。

### 2. Spec-backed Development Mode

该模式吸收 Spec Kit 的阶段产物与规格收敛思想，但仍服从本 skill 的提效优先原则、分级读取、统一门禁和项目记忆规则。不得把所有任务都强制规格化；低风险样式、文案、单点 Bug 和同类实现明确的小改动继续走缩短路径。

命中以下任一条件时，默认进入该模式，除非用户明确要求只给方案或不要生成文件：

1. 需求涉及多模块、跨前后端、数据库、权限、状态流转、接口契约、技术迁移或多页面交互。
2. 原始需求包含多条验收标准，或实现完成后需要逐条证明需求覆盖。
3. 用户明确说"按 Spec Kit 思路"、"先规格再开发"、"保留 spec/plan/tasks"或同义表达。

阶段产物默认写入 `.codex-project/specs/<日期-主题>/`，主题名使用简短英文或拼音短语；路径不明确时使用任务名的安全化短名。最小产物含义：

1. `spec.md`：目标、用户价值、范围边界、验收标准、未知项和非目标。
2. `plan.md`：模块落点、技术方案、关键取舍、数据/接口影响、风险和验证策略。
3. `tasks.md`：按可执行顺序拆分任务，标记依赖、验证点和可并行项。
4. `verification.md`：实际执行的验证命令、观察结果、失败项、未验证范围和证据状态。
5. `convergence.md`：实现结果与 `spec.md`、`plan.md`、`tasks.md` 的逐项对齐结论。

当任务信息足够且未命中第四章硬停条件时，AI 可以直接生成轻量阶段产物并推进实现，不把"等待用户批准 spec"作为默认阻塞点。用户明确要求"先确认规格"、"待我确认"或"不要改代码"时，只生成对应产物和问题，不进入实现。

### 3. 端到端架构流程拆解

用户要求"梳理业务流程"、"画流程图"、"从页面到数据库怎么走"、"技术迁移怎么改"、"替换某个基础组件/中间件/第三方能力"、"先按架构师视角给方案"或同义表达时，进入端到端架构流程拆解模式。该模式吸收 Senior Architect 的系统设计、技术决策和图示输出思想，但不新增外部依赖 skill，不复制外部脚本。

输出应随需求复杂度裁剪，但中高风险需求至少覆盖：

1. 需求类型：业务新增、技术迁移、接口改造、状态流转、跨系统集成、数据迁移或配置部署变更。
2. 影响范围：前端入口、接口契约、服务编排、领域规则、数据表/索引/缓存、外部依赖、配置、部署、监控和权限。
3. 端到端主流程：用户操作或系统触发 → 入参/配置 → 基础校验 → 业务校验 → 数据读写或外部调用 → 返回结果。
4. 异常与分支流程：参数错误、重复数据、权限不足、依赖不可用、兼容性差异、迁移失败、超时、幂等和回滚。
5. 关键决策与取舍：技术选型、兼容策略、灰度策略、数据迁移策略、事务边界、性能和安全考虑。
6. 验证与发布：单测/集成测试、数据一致性、结果一致性、性能基线、监控告警、灰度发布和回滚路径。
7. Mermaid 流程图：用户要求流程图或需求涉及多阶段、多分支时默认输出；纯文字更清晰的小需求可以只输出步骤表。

业务新增类需求的默认链路是：界面输入 → 前端组装参数 → 后端入参 DTO → 基础参数校验 → 业务唯一性/权限/状态校验 → 事务内保存主表和关联表 → 返回成功或错误结果。

技术迁移类需求的默认链路是：现状盘点 → 兼容性评估 → 改造设计 → 环境与配置准备 → 数据迁移或重建 → 双读/灰度/结果对比 → 正式切换 → 监控观察 → 回滚或下线旧能力。

不得把端到端拆解变成空泛架构说明。每个流程节点必须能落到具体模块、接口、数据、配置、验证动作或明确的待确认问题；无法确认的内容标记为未知或待验证，不得凭空补齐。

### 4. 原型产物规则

1. 原型文件默认放 `.codex-project/prototypes/` 或用户指定位置；可用临时 HTML、CSS、JavaScript、图片或静态数据。
2. 原型不得混入正式源码目录，除非用户明确要求转为正式实现。
3. 用户只要求原型或方案时，原型确认前不得改动正式前端页面、接口调用、后端代码或数据库结构。
4. 原型确认后进入正式开发时按第三章读取去重规则执行：只重读被修改过的记忆文件，同类实现位置已查过的不得重复查找。
5. 原型阶段的临时视觉探索、被否决方案和未落地构思不得写入核心业务记忆；只有用户确认或已落地的页面规则、交互规则和数据口径可沉淀。
